# rust-clean-architecture-template

Шаблон REST-сервиса на Rust для команд, которые используют [Go-шаблон](https://github.com/SandQuattro/go-clean-architecture-template). Он нужен сервисам, которые должны переносить резкий наплыв запросов без деградации: у Rust нет сборщика мусора, а при перегрузке сервис быстро отвечает 503, а не копит очередь.

Шаблон повторяет принципы Go-шаблона (слои, ошибки, транзакции, конфигурация, наблюдаемость) и тот же публичный HTTP-контракт: пути, методы, коды ответов, формы JSON, ошибки в `application/problem+json`. Один и тот же k6-сценарий и один и тот же набор интеграционных тестов применимы к обеим версиям.

## Структура workspace

```
crates/
  domain/            сущности, use case (UserService), порт UserRepository, доменные ошибки
  adapter-postgres/  реализация UserRepository на sqlx
  adapter-http/      axum-обработчики, DTO, OpenAPI, отображение ошибок в HTTP
  app/               бинарник clean-arch-template: main, App::new/run, config, database, telemetry, server, router
integration-tests/   reqwest против запущенного приложения (отдельный член workspace)
migrations/          SQL-миграции sqlx (пары .up.sql / .down.sql)
config/              config.toml, config.json
load-test/           сценарии k6
```

Правило зависимостей (проверяется Cargo):

```
domain <- adapter-postgres
domain <- adapter-http
domain, adapter-postgres, adapter-http <- app
```

- `domain` зависит только от `thiserror` и не знает о serde, axum, sqlx, tracing. Деньги — `i64` в минимальных единицах валюты (100 = 1$).
- Адаптеры не зависят друг от друга: `adapter-http` не видит `adapter-postgres` и `sqlx`.
- `app` — единственное место, где адаптеры собираются вместе (`App::new` / `App::run`). Модули `database` и `telemetry` не импортируют `config`, а принимают простые параметры.
- Порты объявляет потребитель: `UserRepository` в `domain`, `UserUseCase` в `adapter-http`.
- Пакеты адаптеров названы с префиксом `adapter-`: пакет `http` конфликтовал бы с крейтом `http`, на котором построен axum.

## Запуск

Весь стек (приложение, PostgreSQL 16, Jaeger, Prometheus, Grafana, интеграционные тесты) через docker compose.

Паролей в репозитории нет. docker compose берёт `DB_PASSWORD` из окружения или из файла `.env`, а `.env` указан в `.gitignore`. Создать `.env` со случайным паролем:

```
echo "DB_PASSWORD=$(openssl rand -hex 16)" > .env
```

Пароль задаётся при создании тома Postgres. После смены пароля нужен `make cleandc`.

```
DEBUG=true ENV_NAME=dev make cleandc   # с очисткой тома Postgres
ENV_NAME=dev make dc                   # том сохраняется
```

Compose-проект называется `rust-cat`, у сервисов нет `container_name`, а порты сдвинуты, чтобы стек можно было поднять одновременно со стеком Go-шаблона:

| Сервис | Адрес на хосте |
|---|---|
| приложение | http://localhost:9001 |
| PostgreSQL | localhost:5435 |
| Jaeger UI | http://localhost:16687 |
| Prometheus | http://localhost:9091 |
| Grafana | http://localhost:3001 (без входа: анонимная роль Admin, порт открыт только на 127.0.0.1) |

Локально (нужны PostgreSQL и обязательные переменные `DB_PASSWORD`, `PG_POOL_MAX`). `make run`, `make docker`, `make migrations-status` и `make k8s-deploy` берут `DB_PASSWORD` только из окружения, `.env` они не читают:

```
set -a; . ./.env; set +a   # DB_PASSWORD из .env в окружение
DB_HOST=localhost DB_PORT=5435 DB_USER=postgres DB_NAME=demo PG_POOL_MAX=4 ENV_NAME=dev make run
```

Тестовая БД и тесты:

```
make test-db        # контейнер rust-cat-test-db на 127.0.0.1:5436, без пароля (trust); ждёт готовности до 30 с
make tests          # DATABASE_URL по умолчанию postgres://postgres@127.0.0.1:5436/postgres
make test-db-drop
```

Тесты `adapter-postgres` используют `#[sqlx::test]` и создают отдельную БД на каждый тест. `make tests` исключает `integration-tests`. Интеграционные тесты запускаются сервисом compose (`make test-integration`) или вручную против работающего приложения:

```
HOST=localhost PORT=9001 cargo test -p integration-tests
```

`SKIP_INTEGRATION_TESTS=1` пропускает их. Другие цели Makefile: `make help`.

`make test-coverage` ставит `cargo-llvm-cov` 0.9.1 в `./bin` и компонент `llvm-tools-preview`, прогоняет тесты workspace без `integration-tests` с инструментированием (нужна та же БД, что для `make tests`) и открывает HTML-отчёт `target/llvm-cov/html`. Инструментированная сборка занимает отдельный каталог `target/llvm-cov-target`.

## API и документация

OpenAPI 3.1 генерируется из типов и обработчиков (aide + schemars). Документация (Scalar): http://localhost:9001/docs, схема: `/openapi.json`.

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/users/{page}/{size}` | страница пользователей (страницы с 1, `size` 1..=1000) |
| GET | `/users-with-orders/{page}/{size}` | страница пользователей с заказами |
| GET | `/user/{id}` | пользователь по ID |
| POST | `/user` | создать пользователя |
| PUT | `/user/{id}` | изменить имя (ID берётся только из пути) |
| DELETE | `/user/{id}` | удалить пользователя |
| POST | `/transfer` | перевод между счетами |

Структурная валидация (garde, неизвестные поля тела отклоняются) даёт 422, бизнес-правила в `domain` дают 400/404/409. Неизвестные ошибки и паники превращаются в обезличенный 500, а текст внутренней ошибки клиенту не уходит. Тела ошибок — `application/problem+json` в форме `ErrorModel` из Huma: массив `errors[]` с полем `location` вида `body.name` или `path.id`.

## Конфигурация

Источники: файл, затем переменные окружения поверх. Путь к файлу: `CONFIG_PATH`, иначе `config/config.toml` или `config/config.json` от рабочей директории (в таком порядке), иначе те же файлы из каталога `config/` репозитория относительно крейта `app`. Docker-образ содержит только `config/config.json`. Ошибка в конфигурации останавливает старт с кодом 1.

Имена переменных совпадают с Go-шаблоном, поэтому compose и k8s-манифест переносятся без изменений. Столбец «Умолчание» — значение, если параметра нет ни в файле, ни в окружении; `config/config.json` задаёт свои значения для части параметров (столбец «config.json»).

| Переменная | Умолчание | config.json | Описание |
|---|---|---|---|
| `CONFIG_PATH` | не задана | | путь к файлу конфигурации |
| `APP_NAME` | пусто | `clean_architecture_template` | имя сервиса (`service.name` в трейсах) |
| `ENV_NAME` | `dev` | `prod` | `prod`: JSON-логи; `dev`: включает dev-маршруты |
| `DEBUG` | `false` | `false` | `true`: уровень debug и логирование SQL; формат булева как в Go `strconv.ParseBool` |
| `HTTP_PORT` | `8000` | `8000` | порт HTTP |
| `HTTP_READ_TIMEOUT` | `10s` | | чтение заголовков запроса и тела запроса (см. ниже) |
| `HTTP_WRITE_TIMEOUT` | `10s` | | пауза между фрагментами тела ответа |
| `HTTP_IDLE_TIMEOUT` | `60s` | | простой keep-alive между запросами |
| `HTTP_REQUEST_TIMEOUT` | `30s` | | обработка API-запроса до готовности ответа, по истечении 503; он же `statement_timeout` соединений пула API |
| `HTTP_SHUTDOWN_TIMEOUT` | `10s` | | предел всей остановки |
| `HTTP_MAX_CONCURRENCY` | `256` | | общий предел одновременных API-запросов, допустимо `1..=Semaphore::MAX_PERMITS` tokio. **Новая** |
| `DB_HOST` | пусто | `postgres` | хост; допускается `host:port` |
| `DB_PORT` | `0` | `5432` | порт; игнорируется, если порт указан в `DB_HOST` |
| `DB_USER` | пусто | `postgres` | пользователь |
| `DB_PASSWORD` | нет | | **обязательна**; пользователь и пароль кодируются в строке подключения (percent-encoding), поэтому допустимы любые символы (в Go не кодируются) |
| `DB_NAME` | пусто | `demo` | имя БД |
| `DB_SSLMODE` | `disable` | | `sslmode` в строке подключения, режимы как в libpq: `disable`, `allow`, `prefer`, `require` (шифрует без проверки сертификата), `verify-ca`, `verify-full` (проверяют сертификат по системному хранилищу; в Docker-образе это набор CA distroless) |
| `MIGRATIONS_DIR` | `migrations` | | каталог миграций на диске |
| `PG_POOL_MAX` | нет | `2` | максимум соединений в пуле, **обязательна** |
| `PG_POOL_MIN` | `1` | | минимум соединений |
| `PG_POOL_CONN_TIMEOUT` | `5` | `2` | секунды: предел одной попытки подключения и пауза между попытками |
| `PG_POOL_HEALTHCHECK` | `1` | `2` | минуты, см. ниже |
| `PG_POOL_ACQUIRE_TIMEOUT` | `2s` | | ожидание свободного соединения из пула. **Новая** |
| `LOG_LEVEL` | `INFO` | `DEBUG` | уровень логов |
| `TRACING_URL` | пусто | `jaeger:4317` | OTLP gRPC-коллектор; пустое значение выключает экспорт трейсов (спаны и `trace_id` в логах остаются) |

Убрана переменная `LOG_BACKEND`: бэкенд логов один (`tracing`). `APP_VERSION` не читается в рантайме: версия подставляется при сборке (`option_env!`, Makefile и Dockerfile передают `git describe --tags --always --dirty`, по умолчанию `dev`).

Длительности (`HTTP_*`, `PG_POOL_ACQUIRE_TIMEOUT`) записываются в формате Go: последовательность `<целое><единица>`, единицы `h`, `m`, `s`, `ms` (например `1m30s`, `500ms`). Допустимы и в файле, и в окружении (в Go — только из окружения). Значение без единицы (`10`) отвечает ошибкой. `PG_POOL_CONN_TIMEOUT` и `PG_POOL_HEALTHCHECK` остаются целыми числами, как в Go.

Нулевые значения `HTTP_READ_TIMEOUT`, `HTTP_WRITE_TIMEOUT`, `HTTP_IDLE_TIMEOUT`, `HTTP_REQUEST_TIMEOUT`, `HTTP_SHUTDOWN_TIMEOUT`, `PG_POOL_ACQUIRE_TIMEOUT` и `PG_POOL_CONN_TIMEOUT` отклоняются при загрузке конфигурации. В Go (Fiber) 0 означает «без ограничения», а здесь каждое ожидание ограничено. Также отклоняются `PG_POOL_HEALTHCHECK=0` (нулевой `idle_timeout` заставил бы чистку пула sqlx работать без пауз), `PG_POOL_HEALTHCHECK`, переполняющий длительность при переводе минут в секунды, и `PG_POOL_MAX=0` (pgxpool тоже требует `MaxConns >= 1`).

Параметры без умолчания в Go (`APP_NAME`, `DB_HOST`, `DB_PORT`, `DB_USER`, `DB_NAME`, `TRACING_URL`) получают нулевые значения Go.

### `PG_POOL_HEALTHCHECK`

В pgxpool `HealthCheckPeriod` — период фоновой проверки соединений. В sqlx такой проверки нет, поэтому `PG_POOL_HEALTHCHECK` (минуты) задаёт `idle_timeout` пула: соединение, простаивающее дольше, закрывается.

Проверка перед выдачей — как в pgxpool: соединение, простоявшее в пуле дольше 1 с, проверяется ping, а разорванное молча заменяется новым. Только что возвращённое соединение выдаётся без проверки, поэтому выдача из пула под нагрузкой не добавляет обращения к БД. `test_before_acquire` sqlx выключен: он пинговал бы перед каждой выдачей. При возврате в пул sqlx пингует соединение всегда, это не настраивается.

## Отличия от Go-шаблона

Соответствие принципов Go-шаблона описано в разделе 9 дизайн-документа; ниже — всё, что реализовано иначе или добавлено.

- **Перегрузка.** В Go нет ни ограничения конкурентности, ни отказа, ни таймаута запроса, которые возвращали бы 503. Здесь они есть (раздел «Поведение при перегрузке»).
- **Транзакции.** В Go репозиторий берёт соединение через `r.db(ctx)`, а транзакция передаётся в контексте. В Rust метод репозитория сам открывает транзакцию (`pool.begin()` … `commit()`), при отбрасывании future транзакция откатывается.
- **Метрики.** Один эндпоинт `/metrics` вместо `/metrics` и `/fiber`. Состав: HTTP-запросы (счётчик и гистограмма по методу, шаблону маршрута и статусу), запросы в работе, счётчик отказов load shed (`http_requests_shed_total`), состояние пула (`db_pool_connections`), метрики процесса, `jemalloc_allocated_bytes` и `jemalloc_resident_bytes`. `/monitor` (дашборд Fiber) не переносится.
- **Логи.** Глобальный фасад `tracing` без внедряемого логгера, один бэкенд. `ENV_NAME=prod` включает JSON (ключ сообщения `message`), `trace_id` и `span_id` добавляются в запись внутри спана; объекты `span` и `spans` не пишутся. `DEBUG=true` включает уровень debug независимо от `LOG_LEVEL`. `domain` и `adapter-postgres` не логируют. Уровень по умолчанию `INFO`. Access-лог, как в Go: сообщение `access`, поля `method`, `path` (шаблон маршрута, как метка метрик), `uri` (путь с query в том виде, в каком пришёл), `ip` (адрес клиента), `status`, `latency_ms`. `LOG_LEVEL` фильтрует только логи: у слоя трейсов свой уровень INFO (с `DEBUG=true` — debug), поэтому `LOG_LEVEL=WARN` не отключает трейсы и `trace_id` в оставшихся записях, как и в Go. При уровне DEBUG внутренние события зависимостей (`h2`, `hyper`, `hyper_util`, `tonic`, `tower`, `opentelemetry*`) ограничены уровнем INFO, события `sqlx` (в том числе события пула) остаются на DEBUG. Спаны `aide` (построение маршрутов при старте) в OTel не экспортируются.
- **Логирование пула.** У sqlx нет трассировщика событий пула, как у pgx. При `DEBUG=true` логируются SQL-запросы и собственные события sqlx уровня debug.
- **TLS к PostgreSQL.** sqlx собран с фичей `tls-rustls-ring-native-roots` (rustls с провайдером ring, без C-сборки aws-lc-rs; корневые сертификаты берутся из системного хранилища, как в pgx). Все шесть режимов `DB_SSLMODE` работают как в libpq: `require` шифрует без проверки сертификата, `verify-ca` и `verify-full` проверяют его по системному хранилищу. В Docker-образе это набор CA distroless; собственный CA нужно добавить в образ.
- **Подключение к БД.** До `CONNECT_ATTEMPTS` (10) попыток, пауза между ними `PG_POOL_CONN_TIMEOUT`. Каждая попытка ограничена таймаутом tokio, потому что у `PgConnectOptions` в sqlx 0.9 нет таймаута подключения. Сигнал остановки прерывает ожидание.
- **HTTP-сервер.** Вместо `axum::serve` используется `hyper_util` `http1::Builder`: `axum::serve` 0.8.9 не настраивает чтение заголовков и ждёт соединения при остановке без дедлайна. Собственный таймер заголовков hyper отключён, потому что он отсчитывался бы и в простое keep-alive. Таймауты по фазам соединения:
  - заголовки: от приёма соединения (или первого байта следующего запроса) не дольше `HTTP_READ_TIMEOUT`, срок суммарный;
  - обработка: таймер соединения не действует, предел задаёт роутер: `HTTP_REQUEST_TIMEOUT` до готовности ответа и `HTTP_READ_TIMEOUT` на чтение всего тела запроса;
  - простой keep-alive после полностью отправленного ответа: `HTTP_IDLE_TIMEOUT`.

  Буфер чтения соединения ограничен 16 KiB: заголовки, которые в него не помещаются, получают 431. У hyper по умолчанию около 408 KiB на соединение, у Fiber предел заголовков 4 KiB.

  `HTTP_WRITE_TIMEOUT` задаёт предел паузы между фрагментами тела ответа. Для ответа из одного фрагмента он практически не действует: после постановки последнего фрагмента в очередь hyper отбрасывает тело.
- **Остановка.** SIGINT или SIGTERM запускают остановку с единым дедлайном D = момент сигнала + `HTTP_SHUTDOWN_TIMEOUT`. Сервер перестаёт принимать соединения. Простаивающие keep-alive и принятые, но не приславшие ни байта, закрываются сразу. Остальные, включая соединение с недочитанными заголовками (как `StateActive` в Go), дренируются до D, затем закрываются принудительно. Закрытие пулов (пул API и пул `/readyz` закрываются одновременно) ограничено `max(D - now, 500 ms)`, сброс трейсов — `max(D - now, 1 s)`. Если бюджет исчерпан, остановка завершается не позже D + 1,5 с.
- **Паники.** Хук паники пишет в лог текст, место и backtrace вместе с `trace_id`; в метриках запрос считается как 500, клиент получает обезличенный 500 problem+json.
- **`PUT /user/{id}`.** Поле `id` в теле отклоняется кодом 422. В OpenAPI Go-версии написано, что оно «игнорируется», что неточно и для самого Go.
- **Стартовая диагностика.** Лог содержит версию, окружение, hostname, PID, число CPU и worker-потоков tokio, домашний каталог, статистику jemalloc и `_RJEM_MALLOC_CONF`. Основной исходящий IPv4 определяется средствами std: UDP-сокет `bind("0.0.0.0:0")` и `connect("8.8.8.8:80")`, затем `local_addr()`. Пакеты при этом не отправляются. Если адрес определить не удалось, пишется `unknown`.
- **Аллокатор.** jemalloc как глобальный аллокатор; профиль кучи работает только в Linux и только в dev.
- **Пароли.** В репозитории нет паролей. Compose берёт `DB_PASSWORD` из окружения или `.env`. Тестовая БД работает без пароля (trust), Grafana открывается без входа; обе доступны только на 127.0.0.1. Secret для k8s создаёт `make k8s-deploy`, а пароли в тестах генерируются при запуске. В Go пароль `admin` записан в compose, Makefile и `k8s.yaml`.
- **Миграции.** Формат sqlx: пары `.up.sql` / `.down.sql`, а не один файл с секциями goose. Схема — одна начальная миграция, сводящая четыре миграции Go в итоговое состояние.

## Поведение при перегрузке

Слои API-роутера (снаружи внутрь):

1. перехват паники, 500 problem+json;
2. серверный спан OpenTelemetry с W3C `traceparent`;
3. HTTP-метрики и access-лог (снаружи от load shed, поэтому отказы видны);
4. перевод ошибок слоёв 5–8 в problem+json;
5. load shed: если лимит занят, немедленный 503 без очереди;
6. общий лимит одновременных запросов `HTTP_MAX_CONCURRENCY` (один семафор на весь API, `GlobalConcurrencyLimitLayer`);
7. таймаут обработки `HTTP_REQUEST_TIMEOUT`, при истечении 503;
8. таймауты тела запроса и тела ответа.

Слои 4–8 действуют на API, включая `/openapi.json` и `/docs`. Пробы `/livez`, `/readyz`, `/`, а также `/metrics` и dev-маршруты в лимит не входят: проба не получает 503 из-за перегрузки API. `/readyz` проверяет БД через отдельный пул из одного соединения с теми же параметрами подключения (предел 1 с) и не стоит в очереди пула API: пул API, исчерпанный при всплеске, не делает пробу неуспешной. Это одно дополнительное соединение с PostgreSQL на реплику. Ожидание соединения из пула ограничено `PG_POOL_ACQUIRE_TIMEOUT` (2 с), а его истечение отдаётся как 503.

Соединения пула API открываются с `statement_timeout` = `HTTP_REQUEST_TIMEOUT`. Когда future запроса отброшен (таймаут запроса, клиент ушёл), sqlx не отменяет запрос в PostgreSQL, а соединение возвращается в пул только после завершения запроса. Предел ограничивает это время на стороне PostgreSQL, включая ожидание блокировок строк: перевод, который ждёт строку, заблокированную другой транзакцией, освобождает соединение и свои блокировки не позже чем через `HTTP_REQUEST_TIMEOUT` от начала оператора. Такое соединение в пул не возвращается: проверка при возврате получает ошибку отмены, sqlx пишет одну строку WARN `error occurred while testing the connection on-release` и закрывает соединение, новое открывается по требованию. Предел передаётся параметром запуска `options`; пулер соединений между приложением и PostgreSQL может отклонять неизвестные параметры запуска (у PgBouncer это задаёт настройка [`ignore_startup_parameters`](https://www.pgbouncer.org/config.html#ignore_startup_parameters), поведение зависит от версии) — тогда параметр нужно разрешить в пулере. Отмена по пределу (SQLSTATE 57014) — не таймаут пула, поэтому маппинг ошибок sqlx отдаёт её как `Internal` (500). Клиент этот 500 практически не видит: таймаут HTTP-запроса начинается раньше оператора и срабатывает первым (503). Миграции выполняются на отдельном соединении без `statement_timeout`. В Go отмена контекста прерывает запрос средствами pgx (CancelRequest), отдельный предел там не нужен. Тело запроса больше лимита axum по умолчанию (2 MiB) даёт 413, в память целиком не читается.

Отказ по лимиту не пишется в лог (при всплеске лог сам стал бы нагрузкой) и виден в access-логе и счётчике `http_requests_shed_total`.

Тело запроса читается внутри лимита. Клиент, который передаёт тело медленно, держит место в лимите до `HTTP_READ_TIMEOUT` (по умолчанию 10 с), поэтому `HTTP_MAX_CONCURRENCY` таких клиентов переводят API в режим отказа 503 на это время. Если сервис доступен медленным или недоверенным клиентам напрямую, без балансировщика, который буферизует тело, `HTTP_READ_TIMEOUT` стоит уменьшить до времени передачи самого большого допустимого тела.

Запрос, отменённый клиентом (соединение закрыто до ответа), не попадает ни в access-лог, ни в `http_requests_total` и гистограмму: future запроса отбрасывается до записи. Уменьшается только `http_requests_in_flight`. Запрос, прерванный по `HTTP_REQUEST_TIMEOUT`, учитывается как 503.

### Подбор `HTTP_MAX_CONCURRENCY`

Значение по умолчанию `256` — начальное. Подбор по k6-сценарию всплеска (`make spike`) и метрикам `/metrics`:

1. Запустить `make spike` и посмотреть в сводке `shed` (доля 503), `unexpected` (доля прочих не-200) и p95 успешных ответов.
2. Если 503 почти нет, а p95 выше порога, лимит слишком велик: запросы копятся внутри сервиса. Уменьшить значение.
3. Если 503 много, а p95 успешных ответов низкий, лимит слишком мал: сервис отказывает при остатке ресурсов. Увеличить значение.

Подбирать нужно при тех же ограничениях ресурсов, что в целевой среде (лимит памяти и CPU контейнера, `PG_POOL_MAX`).

## Наблюдаемость

- **Метрики:** http://localhost:9001/metrics, формат Prometheus. Prometheus опрашивает только `/metrics`: http://localhost:9091. Grafana: http://localhost:3001.
- **Трейсы:** OTLP gRPC на `TRACING_URL`, сэмплер `ParentBased(TraceIdRatioBased(0.6))`, пропагатор W3C TraceContext. Jaeger UI: http://localhost:16687.
- **Профиль кучи** (только Linux, только `ENV_NAME=dev`): jemalloc с `prof:true` включается переменной `_RJEM_MALLOC_CONF` (символы jemalloc с префиксом, поэтому не `MALLOC_CONF`). В compose переменная передаётся как `MALLOC_CONF`:

  ```
  MALLOC_CONF=prof:true,prof_active:true,lg_prof_sample:19 ENV_NAME=dev make cleandc
  make heapprof                                   # сохраняет /debug/pprof/heap в app.heap
  go tool pprof -http=:8080 app.heap
  ```

  Имена функций добавляет фича `symbolize` крейта `jemalloc_pprof`: символизация идёт в приложении при запросе профиля (через `backtrace`), по символам самого бинарного файла, поэтому `strip` в релизной сборке включать нельзя. Для `go tool pprof` бинарный файл не нужен.

  Без запуска с профилированием эндпоинт отвечает 503, на macOS и других ОС, кроме Linux, — 501.
- **CPU-профилирование:** эндпоинта нет, используются внешние инструменты: `perf record -g -p <pid>` (Linux) или `samply record -p <pid>`.
- **Бенчмарк** горячего пути `users-with-orders` (`make bench`, criterion): 1000 пользователей по 10 заказов, преобразование в DTO и `serde_json::to_vec` занимают 280,8 мкс на итерацию (Apple M4 Pro). Это измерение только преобразования и сериализации, а не всего сервиса.

## Миграции

Миграции читаются с диска из `MIGRATIONS_DIR` (по умолчанию `migrations`), как в Go: менять их можно без пересборки, а Dockerfile копирует каталог в образ. Они применяются при старте на отдельном соединении (без `statement_timeout` пула API) под advisory lock PostgreSQL, который берёт sqlx. Ошибка миграции, включая отсутствующий каталог, останавливает старт. Down-миграции в рантайме не выполняются, только через `sqlx migrate revert`.

```
make new-migration name=add_something   # создаёт пару .up.sql / .down.sql
make migrations-status                  # статус в БД compose (порт 5435)
make sqlx-prepare                       # обновить офлайн-данные запросов (.sqlx/)
```

В нескольких репликах в production миграции лучше запускать отдельным Job или initContainer.

## Нагрузочное тестирование и сравнение с Go

Сценарии k6 лежат в `load-test/`. Используется локальный k6, если он установлен, иначе образ `grafana/k6:2.2.0` в docker (`--network host`). `--network host` работает только с docker на Linux. На macOS нужен локальный k6 или `BASE_URL=http://host.docker.internal:9001`. Итог каждого прогона записывается в `k6-results/<сценарий>-<цель>.json` (каталог в `.gitignore`).

```
make load  [BASE_URL=http://localhost:9001] [TARGET=rust]
make spike [BASE_URL=http://localhost:9001] [TARGET=rust]
```

- `load_test.js` — сценарий Go-шаблона: 30 с до 50 VU, 1 мин на 50 VU, 30 с до 0; пороги `http_req_failed < 1%` и p95 < 200 мс. Страница исправлена на `/users/1/100`: в Go-сценарии стоит `/users/0/100`, а страницы нумеруются с 1, поэтому там запрос всегда получает 422.
- `spike_test.js` — executor `ramping-arrival-rate`: 50 запросов/с (30 с), скачок до 2000/с (5 с), 2000/с (30 с), спад до 50/с (5 с), 50/с (30 с); `preAllocatedVUs` 500, `maxVUs` 2000. 80% запросов `GET /users/1/100`, 20% `GET /users-with-orders/1/100`. Ожидаемый ответ только 200. Метрика `shed` — доля 503, `unexpected` — доля прочих не-200. Пороги информационные: `unexpected < 1%`, p95 успешных ответов < 200 мс; их нарушение не блокирует приёмку.

При нарушении любого порога (в том числе информационного) k6 завершается с кодом 99, и `make` сообщает об ошибке. Итог прогона в `k6-results/` при этом записан.

Метод сравнения: оба сценария прогоняются против Go-стека (приложение на `9000`) и Rust-стека (`9001`) на одной машине поочерёдно, с одинаковыми условиями: лимит памяти контейнера 256M, одинаковый `PG_POOL_MAX`, PostgreSQL 16. Измеряются RPS, p50/p95/p99 успешных ответов, доля 503, доля прочих 5xx и пиковый RSS контейнера (`docker stats`). Набор `integration-tests` дополнительно прогоняется против Go-стека; расхождения, вызванные известными отличиями (503 есть только в Rust), описываются отдельно.

- RPS задаёт сценарий: в `load` 50 VU с паузой 1 с, в `spike` поток до 2000 запросов/с. Оба стека выполнили все итерации без пропусков, поэтому RPS одинаков. При 2000 запросах/с ни один стек не насыщен: по метрике `vus` k6 одновременно были заняты не больше 4 (Rust) и 6 (Go) VU. Отказов и ошибок нет, информационные пороги обоих сценариев выполнены у обоих стеков.
- Максимальная латентность в `spike`: Rust 26,7 мс, Go 228 мс.
- Каждая строка — один прогон. Разброс виден по трём прогонам `spike` у Rust (основной, с `HTTP_MAX_CONCURRENCY=16` и первые 40 с прогона с SIGTERM): p99 от 4,2 до 4,8 мс, пик памяти по `docker stats` от 48 до 62 MiB. Разницу p50 в сотые доли миллисекунды значимой считать нельзя.

**Остановка под нагрузкой.** Повтор `spike`, на 40-й секунде (пик, 2000 запросов/с) — `docker compose -p rust-cat kill -s SIGTERM app`. Контейнер завершился с кодом 0 через 0,14 с после сигнала (по `FinishedAt`), предел — `HTTP_SHUTDOWN_TIMEOUT` (10 с) плюс 2 с. В момент сигнала было открыто 498 соединений; от начала дренажа до `Server stopped` прошло 2,5 мс, `ShutdownTimeout` в логе нет. 135 запросов, отправленных в keep-alive соединения в момент их закрытия, получили `connection reset by peer`. Остальные запросы после остановки получили `connection refused`. Ответов 5xx не было.

**`/readyz` под нагрузкой.** Во время `spike` проба опрашивалась раз в секунду: у Rust 105 ответов 200 из 105, самый долгий 5 мс; у Go 105 ответов 200 из 105, один ответ на пике занял 1,0 с. При 2000 запросах/с пул API не исчерпывался (503 по таймауту пула не было). Поэтому исчерпание пула проверено отдельно: транзакция в psql держит блокировку строки пользователя 1, а два перевода 2→1 ждут её и занимают оба соединения пула (`PG_POOL_MAX=2`).
- Rust: `/readyz` ответил 200 за 2 мс, `GET /users/1/1` — 503 через 2,0 с (`PG_POOL_ACQUIRE_TIMEOUT`, строка WARN `service unavailable` с причиной `pool timed out`).
- Go: `/readyz` и `GET /users/1/1` ждали освобождения соединения 10,5 с, затем ответили 200.

**Подбор `HTTP_MAX_CONCURRENCY` (один шаг).** В основном прогоне `spike` доля 503 равна 0, а p95 равен 1,75 мс при пороге 200 мс: ни одно условие правила подбора не выполняется. Опрос `http_requests_in_flight` раз в секунду в прогоне с SIGTERM (до сигнала, включая 5 с пика) показал не больше 7 запросов в работе, включая сам запрос `/metrics`. Шаг: `spike` с `HTTP_MAX_CONCURRENCY=16`. Результат: 245 отказов (0,33 %), все — load shed (`http_requests_shed_total` = 245, 503 по таймауту пула нет); p95 1,77 мс, p99 4,79 мс. Латентность не улучшилась, а кратковременные всплески параллельности (короче интервала опроса) превысили 16. Значение по умолчанию остаётся `256`.

**Проверка соединения при возврате в пул.** Трафик PostgreSQL записан при постоянных 300 запросах/с `GET /users/1/100` в течение 10 с (3001 запрос).
- Rust: на каждый запрос два обмена с PostgreSQL — сам запрос (пакет 71 байт) и отдельный `Sync` (5 байт, 3002 пакета). PostgreSQL отвечает на `Sync` через 45 мкс (медиана, p90 150 мкс).
- Go: один обмен на запрос (3001 пакет запроса), отдельных `Sync` нет.

На стенде выше лишний обмен пропускную способность не ограничивал: пул из двух соединений не исчерпывался.

**`integration-tests` против Go-стека** (`HOST=localhost PORT=9000`): 12 тестов из 12 проходят. Известное отличие (503 есть только в Rust) набор не проверяет. Вне набора: Go добавляет в тела ответов поле `$schema` и заголовок `Link` (Huma), Rust их не добавляет.
